# Архітектура

[English](../en/architecture.md) · [Зміст документації](README.md)

Ковчег складається з двох половин: **індексування**, яке перетворює документи на модуль (базу знань), і **відповіді**, яка перетворює запитання на джерела й відповідь. Вони зустрічаються у форматі модуля — теці зі звичайними файлами, яку можна копіювати між комп'ютерами.

## Карта пакета

| Модуль | Відповідальність |
|---|---|
| `config.py` | налаштування (`kovcheg.toml`, застарілий `config.json`), структура домашньої теки |
| `readers.py` | PDF (один розділ на сторінку), DOCX і Markdown (розділи за заголовками), HTML, текстові формати, ZIM (кожна стаття) |
| `chunking.py` | фрагменти з урахуванням структури: абзаци → рядки → речення, ніколи не перетинають межу сторінки чи розділу |
| `embedding.py` | протокол `Encoder`; BGE-M3 (щільні + розріджені); енкодер на основі хешування без моделі для тестів |
| `builder.py` | інкрементне атомарне збирання модулів |
| `store.py` | формат модуля v2: засіб запису та `ModuleIndex` лише для читання |
| `security.py` | ключі Ed25519, підписування, глибока перевірка з кешем |
| `migrate.py` | перетворення модулів прототипу (`search_bge.db`) без повторного кодування |
| `retrieval.py` | BM25, щільний і розріджений пошук, зважений RRF, дедуплікація, різноманітність, розширення контексту |
| `rerank.py` | реранкінг крос-енкодером (BGE reranker v2-m3) |
| `generation.py` | побудова промпту в межах бюджету токенів, генерування через llama.cpp, перевірка посилань |
| `engine.py` | фасад `Kovcheg`, який використовують CLI та UI: ліниве завантаження моделей, перевірка доказів, стани |
| `cli.py`, `ui/` | командний рядок та інтерфейс на Streamlit |

Важкі бібліотеки (PyTorch, llama.cpp, Streamlit, читачі PDF/DOCX/ZIM, cryptography) імпортуються лише всередині функцій, яким вони потрібні. Для `import kovcheg` і пошуку за ключовими словами достатньо самого numpy.

## Індексування

1. **Читання.** Кожен файл перетворюється на список розділів `(text, page, heading)`. PDF зберігають номери сторінок, які потім показує кожне посилання. DOCX і Markdown зберігають заголовки. Сторінки HTML і ZIM очищуються від скриптів, навігації та нижніх колонтитулів за допомогою HTML-парсера зі стандартної бібліотеки. Файли, які неможливо прочитати (бінарні, скановані PDF без тексту), пропускаються й наводяться в звіті про збирання із зазначенням причини.
2. **Поділ на фрагменти.** Розділи поділяються на абзаци, рядки й речення (зокрема з урахуванням пунктуації CJK) і пакуються у фрагменти приблизно по 1000 символів (щонайбільше 1600) з перекриттям в одне речення. Фрагменти ніколи не перетинають межу сторінки чи розділу. До тексту, що надсилається моделі ембедингів, додається префікс `title — section:`, щоб фрагмент на кшталт «тисніть на рану 10 хвилин» кодувався разом зі своїм контекстом («Кровотеча — Рани кінцівок»). Збережений текст залишається незмінним.
3. **Кодування (необов'язково).** BGE-M3 створює для кожного фрагмента 1024-вимірний щільний вектор і розріджені лексичні ваги. Без енкодера (`--no-embed`) будується лише повнотекстовий індекс.
4. **Зберігання.** Одна база даних SQLite (документи, фрагменти, повнотекстовий індекс FTS5, розріджені ваги кожного фрагмента), матриця векторів float16 (`dense.f16.npy`) і розріджений інвертований індекс (`sparse.npz`). Обидва масиви не стиснуті, щоб їх можна було відображати в пам'ять.
5. **Інкрементні оновлення.** Документи зіставляються за шляхом і SHA-256. Незмінені документи зберігають свої вектори, які копіюються з попередньої матриці без повторного кодування. Змінені документи переіндексовуються, а видалені — вилучаються. Статті ZIM відстежуються окремо, тож повторний запуск ніколи їх не дублює. Зміна енкодера чи налаштувань поділу на фрагменти запускає повне переіндексування з повідомленням про причину.
6. **Атомарне завершення.** Збирання працює в прихованій теці поруч із модулем і замінює модуль перейменуванням лише тоді, коли все записано: базу даних переведено в режим журналу відкату (rollback journal), записано маніфест із хешами SHA-256 усіх файлів, а якщо існує приватний ключ, модуль підписано. Виняток або Ctrl-C видаляє робочу теку й залишає попередній модуль недоторканим.

## Відповідь

```
запитання
  ├─ BM25 (SQLite FTS5)              доступний завжди
  ├─ щільний (BGE-M3, float16)       якщо модуль зібрано із завантаженим енкодером
  └─ розріджений (лексичний BGE-M3)  так само
        │  зважене Reciprocal Rank Fusion (типові ваги dense 1.0, bm25 0.8, sparse 0.6)
        ▼
  дедуплікація (ідентичний текст, майже ідентичні вектори) → щонайбільше 3 збіги на документ
        ▼
  реранкінг топ-20 крос-енкодером (необов'язково)
        ▼
  перевірка доказів ── не пройдено ──► стан "no_evidence": мовна модель не викликається; найближчі уривки показано як малодоречні
        │ пройдено
  розширення контексту: сусідні фрагменти кожного збігу об'єднуються в його контекст
        ▼
  промпт із пронумерованими джерелами в межах бюджету токенів ──► локальна мовна модель (llama.cpp, власний шаблон чату моделі)
        ▼
  перевірка посилань: кожне [n] має посилатися на надане джерело
```

**Чому три методи пошуку.** Щільні вектори знаходять перефразування й працюють між мовами («як зупинити кровотечу» знаходить «control of haemorrhage»). Розріджені ваги BGE-M3 і BM25 знаходять рідкісні точні рядки, які щільні вектори розмивають: назви ліків, коди МКХ на кшталт `J18.9`, номери деталей, дози на кшталт `500 mg`. Крім того, BM25 працює взагалі без моделі, і саме завдяки цьому Ковчегом можна користуватися на будь-якому комп'ютері.

**Злиття.** Reciprocal Rank Fusion поєднує ранги, а не сирі оцінки, тож методи пошуку з непорівнянними шкалами оцінок можна змішувати без калібрування. Внесок кожного методу зважується. Модуль, що пропонує лише BM25, нормалізується на вагу, яку він може запропонувати, тож він чесно конкурує з повністю векторизованими модулями. Сирі оцінки BM25 непорівнянні між модулями різного розміру, тому кандидати BM25 упорядковуються передусім за тим, скільки змістових слів запитання вони містять.

**Запит FTS5.** Запитання розбивається на токени. Кожен токен береться в лапки, щоб пунктуація на кшталт `J18.9` не ламала синтаксис запиту, а токени об'єднуються через OR. Для кодів, чисел з одиницями вимірювання, а також для всього запитання, якщо воно коротке, додаються збіги за фразою.

**Мало пам'яті.** Щільний пошук множить запит на матрицю float16 блоками (за раз — близько 64 МБ робочого простору float32) і підтримує поточний top-k. Тому використання оперативної пам'яті не зростає з розміром бібліотеки. Розріджений індекс читається через масиви, відображені в пам'ять. Відкриті модулі зберігаються в невеликому LRU-кеші, який помічає перезбирання модуля (ідентичність файлу, розмір і час зміни) і відкриває його заново.

**Перевірка доказів.** Якщо є реранкер, найкращий логіт, нижчий за `rerank.min_score` (типово −6), означає, що доречного нічого немає. Без реранкера чи щільного пошуку принаймні одне змістове слово запитання (без урахування закінчень) має траплятися в джерелі. Інакше OR-запит за ключовими словами збігався б майже з будь-чим через одне поширене слово. Якщо перевірку не пройдено, мовна модель не викликається. Сказати «у бібліотеці немає» безпечніше, ніж упевнено вгадувати.

**Генерування.** Джерела нумеруються `[1] … [n]` у порядку рангу, кожне — з посиланням (документ, сторінка, розділ) і своїм текстом разом із сусідніми фрагментами. Якщо промпт перевищив би `context_window − max_tokens`, джерела з найнижчим рангом спершу втрачають сусідні фрагменти, а потім відкидаються. Бюджет вимірює власний токенізатор моделі, якщо він доступний. Ковчег використовує API chat completion з llama.cpp, тож застосовується шаблон чату, збережений у файлі GGUF: підійде будь-яка інструктивна модель. Для моделей без системної ролі інструкції об'єднуються з реплікою користувача. Системний промпт вимагає відповідати лише на основі джерел, ставити посилання після кожного твердження, копіювати числа й дози точно, прямо зазначати, коли джерел недостатньо, і відповідати мовою запитання.

**Перевірка посилань.** Після генерування розбирається кожне `[n]`. Номери поза наданими джерелами позначаються як недійсні, а до відповіді без посилань додається попередження звірити її з джерелами. `Answer.hits[n-1]` — це завжди джерело `[n]` у CLI, UI та виводі JSON.

**Стани.** `ok`, `no_evidence`, `search_only` (немає мовної моделі або запитано лише пошук), `llm_unavailable` (модель налаштовано, але її не вдалося завантажити; джерела все одно повертаються), `error` (генерування завершилося помилкою; джерела зберігаються). Відсутні моделі ніколи не зупиняють систему; вони з'являються як попередження та в `kovcheg doctor`.

## Паралельність

Один рушій `Kovcheg` обслуговує весь вебінтерфейс. Блокування серіалізують виклики енкодера, реранкера й мовної моделі, які не є потокобезпечними й на малому процесорі однаково не працювали б швидше паралельно. Модулі відкриваються лише для читання (`immutable=1`), тож застосунок ніколи не змінює жодного файлу, і хеші залишаються дійсними.
